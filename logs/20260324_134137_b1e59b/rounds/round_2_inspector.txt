## Summary
Round 2 is materially better than Round 1. It fixes most of the earlier problems: the Microsoft Store direction is broadly corrected, the fee comparison is more careful, and the backend-owned entitlement model is now the right core recommendation.

I re-checked the main claims against current official docs from [Stripe](https://docs.stripe.com/webhooks/process-undelivered-events), [Apple](https://developer.apple.com/news/?id=xqk627qu), [Google Play](https://developer.android.com/google/play/billing/lifecycle/subscriptions), and [Microsoft](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies-change-history). One high-severity issue remains, plus several medium gaps around account linking and data modeling.

## Issues Found
- [HIGH] The launch plan still postpones billing correctness until after sales start
- Location: Section 7, `Day 2: add webhook monitoring and idempotency`
- Problem: This contradicts section 6’s own “minimum-safe entitlement flow.” If the user starts selling on Day 1 without verified, duplicate-safe webhook handling, first-day payments can be applied twice, missed entirely, or overwritten by retries/out-of-order deliveries. Stripe’s docs explicitly show retries and duplicate-safe processing as required integration behavior.
- Fix: Move raw-body handling, signature verification, event deduplication, provider-state fetch, and transactional entitlement updates into Day 1. Day 2 can add alerts/dashboards, not base correctness.
```ts
app.post('/webhooks/stripe', raw({ type: 'application/json' }), async (req, res) => {
  const sig = req.headers['stripe-signature'];
  const event = stripe.webhooks.constructEvent(
    req.body,
    sig,
    process.env.STRIPE_WEBHOOK_SECRET
  );

  await db.tx(async (tx) => {
    const inserted = await tx.query(
      `insert into provider_events(provider, event_id)
       values ('stripe', $1)
       on conflict do nothing
       returning 1`,
      [event.id]
    );
    if (inserted.rowCount === 0) return; // duplicate retry

    const subId = extractSubscriptionId(event);
    if (!subId) return;

    const sub = await stripe.subscriptions.retrieve(subId);
    await upsertEntitlementFromStripe(tx, sub); // map current provider truth, not webhook payload
  });

  res.sendStatus(200);
});
```

- [MEDIUM] The Payment Links fix is still not safe enough
- Location: Section 6, `For Stripe Payment Links specifically`
- Problem: `client_reference_id` on a Payment Link is a URL parameter meant for reconciliation, not authenticated identity. A user can alter it before paying. If the backend grants premium directly from that field, entitlements can be attached to the wrong account.
- Fix: Keep `Checkout Sessions` as the primary recommendation. If Payment Links are ever used, require a signed short-lived binding token and verify it server-side before granting access.
```ts
const token = jwt.sign(
  { sub: user.id, purpose: 'billing-link', exp: Math.floor(Date.now() / 1000) + 900 },
  process.env.BILLING_LINK_SECRET
);

// webhook
const claims = jwt.verify(session.client_reference_id, process.env.BILLING_LINK_SECRET);
if (claims.purpose !== 'billing-link') throw new Error('invalid token');
grantEntitlement(claims.sub);
```

- [MEDIUM] Apple account-linking guidance is still incomplete
- Location: Sections 4 and 6, Apple/iOS guidance
- Problem: The answer says “use Apple IAP” but omits Apple’s `appAccountToken`, which is the server-generated UUID Apple returns in transaction data to map purchases to your internal user. It also does not explicitly state the App Review rule that multiplatform access to externally bought subscriptions/features normally requires the same entitlement to be available as IAP in the iOS app, unless the app clearly fits an exception such as companion/enterprise/reader app categories.
- Fix: Add an Apple-specific paragraph: generate a UUID per user, pass it as `appAccountToken`, process App Store Server Notifications/API on the backend, and spell out the `3.1.3(b)` vs `3.1.3(f)` decision rule.
```swift
let token = UUID(uuidString: user.appAccountToken)!
let result = try await product.purchase(options: [.appAccountToken(token)])
```

- [MEDIUM] The proposed storage model is too flat for a multi-provider app
- Location: Section 5, `Your backend should store at least`
- Problem: Listing singular fields like `provider`, `provider_customer_id`, and `provider_subscription_id` suggests one billing record per user. That breaks once the same user has Stripe web billing plus Apple/Google purchases, migrations, restores, refunds, or overlapping access windows.
- Fix: Separate provider accounts, subscriptions, raw events, and derived entitlements.
```sql
create table billing_accounts (
  id uuid primary key,
  user_id uuid not null,
  provider text not null,
  provider_customer_id text,
  unique (provider, provider_customer_id)
);

create table subscriptions (
  id uuid primary key,
  billing_account_id uuid not null,
  provider_subscription_id text not null,
  status text not null,
  unique (billing_account_id, provider_subscription_id)
);

create table provider_events (
  provider text not null,
  event_id text not null,
  primary key (provider, event_id)
);
```

- [LOW] The Microsoft Store citation is no longer the current one
- Location: Section 1 and Sources list
- Problem: The answer cites archived policy `7.16.1` as “current,” but Microsoft updated Store policies through `7.19` on September 10, 2025, including `10.8.x` changes and a Partner Center checkbox requirement when using third-party purchase APIs. The broad conclusion may still hold, but the citation is stale.
- Fix: Update the source to Microsoft’s latest Store policy/change-history page and mention the third-party billing disclosure checkbox explicitly.

## Improvement Suggestions
- Highest impact: Move the entire “minimum-safe entitlement flow” into the Day 1 launch scope. Monitoring can wait; correctness cannot.
- High impact: Add an Apple-specific implementation block covering `appAccountToken`, App Store Server Notifications, and when external web entitlements are allowed in iOS.
- High impact: Replace the flat field list with a normalized billing model: `billing_accounts`, `subscriptions`, `provider_events`, `entitlements`.
- Medium impact: Remove Payment Links from the main recommendation entirely unless they are wrapped in a signed binding flow.
- Medium impact: Refresh the Microsoft Store citation to the latest policy version and note the Partner Center disclosure requirement.
