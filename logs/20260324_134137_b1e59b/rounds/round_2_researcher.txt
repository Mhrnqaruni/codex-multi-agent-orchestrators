6. Minimum-safe entitlement flow

For web and direct Windows:
- create checkout sessions server-side only,
- attach your internal user ID using Stripe `client_reference_id` or provider metadata,
- redirect the user to a hosted checkout page,
- verify the webhook signature,
- deduplicate the event,
- fetch the latest subscription state from the provider,
- then update your entitlement.

For Apple and Google:
- never trust the device alone,
- verify purchases server-side,
- store provider tokens/IDs,
- listen for server notifications,
- and re-check provider state before changing premium access.

Security checklist:
- verify Stripe webhook signatures,
- verify PayPal webhook signatures or use PayPal’s verification endpoint,
- use raw request bodies where the provider requires them,
- deduplicate events by provider event ID,
- ignore stale/out-of-order events using event timestamps,
- derive entitlement from current provider truth, not only from the webhook payload,
- support `grace`, `pending`, `on_hold`, and restore flows,
- do not unlock premium purely from client-side receipts or local flags.

For Google specifically:
- use `purchases.subscriptionsv2.get()` on your backend,
- handle RTDN,
- acknowledge new purchases within 3 days,
- pass `setObfuscatedAccountId()` / `setObfuscatedProfileId()` so purchases can be tied back to your internal user safely.

For Stripe Payment Links specifically:
- only use them if you pass `client_reference_id`,
