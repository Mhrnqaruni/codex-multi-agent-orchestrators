## Issues Found
- [HIGH] The launch plan still defers UK consumer cancellation/compliance until after sales start
- Location: `Realistic 1 to 2 day launch plan` -> `Day 2: add billing management and cancellation flow`
- Problem: For a UK web/direct-Windows launch, cancellation and digital-content consent are not optional Day 2 extras. GOV.UK says for downloads/streaming/digital services you must provide cancellation information, confirm the contract in a durable form, and if access starts immediately, get the customer to acknowledge losing the 14-day cancellation right before supply starts. If you launch without this, you create immediate compliance/refund risk.
- Fix: Move cancellation, contract confirmation, and immediate-access consent into Day 1. At minimum, record consent before creating checkout and give the user a self-service cancellation path immediately.
```ts
if (!req.body.instantAccess || !req.body.loseCancellationRight) {
  return res.status(400).json({ error: 'Digital-content consent required' });
}
await db.query(
  `insert into consumer_consents (user_id, terms_version, consented_at)
   values ($1, $2, now())`,
  [req.user.id, TERMS_VERSION]
);
```
Use Stripe’s customer portal on Day 1 for cancellation/billing management, not Day 2.

- [MEDIUM] Account-linking is improved, but restore and out-of-band purchase claiming are still missing
- Location: `Platform-specific rules you must design around` -> iOS `appAccountToken`; Android `setObfuscatedAccountId()`
- Problem: This no longer has the old flat-model bug, but it still overstates how complete the linking solution is. Apple documents `appAccountToken` as optional, and Google explicitly notes purchases made outside the app may not have these identifiers. Without a backend claim/restore flow, legitimate purchases can become orphaned or linked to the wrong account.
- Fix: Add a signed `claim purchase` flow for Apple and Google: user logs in, sends `originalTransactionId` or `purchaseToken`, backend fetches provider truth, locks the record, and links it only if unclaimed.
```ts
await db.tx(async (tx) => {
  const owner = await tx.oneOrNone(
    `select user_id from subscriptions
     where provider = $1 and provider_subscription_id = $2
     for update`,
    [provider, providerSubId]
  );
  if (owner && owner.user_id !== req.user.id) throw new ConflictError();
  await linkVerifiedPurchase(tx, req.user.id, verifiedPurchase);
});
```

- [MEDIUM] Cross-provider entitlement conflict resolution is still underspecified
- Location: `Architecture that is safe and scalable` / `Normalized billing model`
- Problem: The schema direction is now correct, but the derivation rule is still missing. This is an architectural inference from the multi-provider model: one provider’s `expired` or `revoked` event must not turn off access that is still valid from another provider. Without an explicit union rule, a stale Stripe expiry can overwrite an active Apple or Google entitlement.
- Fix: Define entitlements as derived from all active grants, not from the last processed provider event.
```sql
with grants as (
  select ba.user_id, max(s.current_period_end) as access_until
  from subscriptions s
  join billing_accounts ba on ba.id = s.billing_account_id
  where s.status in ('active','trialing','grace')
  group by ba.user_id
)
update entitlements e
set is_premium = g.access_until > now(),
    access_until = g.access_until
from grants g
where e.user_id = g.user_id;
```

- [MEDIUM] Mobile notification authenticity is still not explicit enough
- Location: `The Day 1 minimum-safe billing flow` and mobile platform sections
- Problem: The answer correctly says not to trust webhook payloads directly, but it only spells that out concretely for Stripe. For Apple and Google, it says to process notifications and fetch provider truth, but it does not explicitly require verifying notification authenticity first. Apple’s server notifications deliver signed data, and Google Pub/Sub push subscriptions support signed OIDC JWTs. Leaving this implicit is a real spoofing risk.
- Fix: Add notification-auth verification to the minimum-safe checklist for Apple/Google.
```ts
const appleNotif = await appleVerifier.verifyAndDecodeNotification(req.body.signedPayload);

const claims = await verifyPubSubJwt(req.get('Authorization')!, EXPECTED_AUD);
if (claims.email !== EXPECTED_SERVICE_ACCOUNT || !claims.email_verified) {
  return res.sendStatus(401);
}
```

## Improvement Suggestions
- Highest impact: Move UK consumer-law readiness into the Day 1 checklist: cancellation path, immediate-access consent, saved contract copy, refund/cooling-off handling.
- High impact: Add explicit restore/claim endpoints for Apple and Google so purchases made outside the active logged-in session can still be safely attached.
- High impact: State the entitlement merge rule directly: access is the union of all active providers, and one provider cannot revoke another provider’s still-valid grant.
- Medium impact: Add a Day 1 Stripe customer-portal flow so users can cancel/manage billing immediately.
- Medium impact: Mention [Stripe Managed Payments](https://docs.stripe.com/payments/managed-payments) as another merchant-of-record option to evaluate later; it is relevant, but its current public-preview status still makes Paddle the cleaner MoR recommendation in this answer.
